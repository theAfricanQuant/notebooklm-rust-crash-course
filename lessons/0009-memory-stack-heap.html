Where does Rust keep your data?

See the simple difference between stack memory for fixed-size values and heap memory for data that can grow.

35–45 minutesOne small programStack and heap

The big idea

When a program runs, it needs a place to keep its working data. That place is RAM—the computer’s short-term workspace. It is different from your SSD or hard drive, where files stay saved after the program closes.

Rust uses two important areas in a program’s memory: the stack and the heap. They are two ways to organize working data. These names are related to, but not exactly the same as, the stack and heap data structures from an algorithms class.

As a first model, picture fixed-size values such as an i32 going directly into a stack slot. A value that can grow, such as a String, uses flexible space on the heap.

Course source: Tech With Tim’s Rust Programming Tutorial.

RAM is the program’s workbench

Imagine you are doing homework. Your saved files are in a folder on your computer. While you work, you also need a desk for the book, paper, and calculator you are using right now. RAM is like that desk: it holds data programs need quickly while they are running.

The stack and heap are two parts of a program’s RAM workspace. The stack is neat and follows a clear order. The heap is more flexible and is useful when data can change size.

The stack: last in, first out

Think of a stack of cafeteria trays. You put each new tray on top. When you take one, you take the top tray first. So the last tray in is the first tray out.

Programmers call this LIFO: “Last In, First Out.” You may also hear FILO: “First In, Last Out.” They describe the same order. The newest item is removed first.

Rust uses this order to keep track of active function calls. Each time a function calls another function, the new call’s working area goes on top of the stack. When that function finishes, its working area comes off, and the program returns to the function below it.

main starts         stack: [main]
main calls calculate stack: [main, calculate]
calculate calls add  stack: [main, calculate, add]
add finishes        remove add; return to calculate
calculate finishes  remove calculate; return to main
main finishes       remove main

The i32 number 95 has a known, fixed size, so it fits in a predictable stack slot in our simple model. Stack work is quick because Rust knows which function is active and which work area to remove next.

If a program keeps calling functions without finishing them—for example, runaway recursion—the stack can run out of room. Most beginner programs will not need to manage the stack directly.

The heap: flexible space

Now picture a storage room where you can ask for a space that fits what you need. That is a useful way to imagine the heap. A growable String might hold a short word now and more text later, so Rust asks a helper called the memory allocator to find room for the text.

The String value itself is small enough to fit on the stack. It carries three useful details: a pointer (where its text is), a length (how many bytes of text are in use), and a capacity (how many bytes of room have been reserved). The actual text characters are in the heap space.

To read the text, the program follows the pointer from the stack to the heap. Asking for heap space and following that pointer can take extra work compared with reading a simple number directly. That does not mean you should avoid String; use it when you need growable text. Rust makes both kinds of memory useful.

How do languages clean up memory?

RAM is limited, so a program should stop using data when it is finished with it and make that space available again.

Some languages use a garbage collector. Think of it as a helper that checks which heap objects the program can still reach. When an object is no longer in use, the collector can reclaim its space. Java and C# use garbage collectors. Python also manages memory automatically, so Python programmers usually do not free objects by hand.

Rust does not use a general garbage collector to scan the program while it runs. Instead, Rust checks ownership rules as you compile. When an owned value such as a String goes out of scope, Rust runs its cleanup code and releases the string’s heap allocation. This predictable cleanup is one reason Rust can manage memory without a garbage collector.

We will study the ownership rules in the next topic. For today, remember: a garbage collector is one way to find unused memory; Rust uses ownership to know when owned data can be cleaned up.

Step 1 · one fixed-size value

Put an integer to work

Replace the contents of src/main.rs with this:

fn main() {
    let score: i32 = 95;
    println!("Score: {score}");
}

Run cargo fmt && cargo run. You should see Score: 95. An i32 always has the same size, so it is a good example of a value stored directly in a stack slot.

Step 2 · text that can grow

Add a String

Add these lines inside main, just below the score line:

let language = String::from("Rust");
println!("Language: {language}");
println!("Text length: {} bytes", language.len());

Save and run again. You should see the language and a length of 4. The language variable has a small handle on the stack; its text lives in flexible heap space. String::from makes an owned, growable string from the text.

Change "Rust" to "Rust is fun!" and run again. The string now has more text, so its length becomes 12 bytes. These example letters, spaces, and punctuation each use one byte.

When the function is done

At the end of main, its local work is finished. Rust removes that function’s working area from the top of the stack. The String also runs its cleanup code, which releases the heap space holding "Rust is fun!".

You did not have to tell Rust how many bytes to free or where to find them. Rust’s rules and the String type handle that. The next topic explains ownership—the rule that tells Rust when it is safe to clean up a value.
